# Metro Web 009: bind a route transcript to a client challenge

Stage 009 extends the [independent checker](metro-web-008-independent-checker.md)
to reject an unchanged, previously recorded response to `POST /api/site/run`.
It remains a bounded, read-only experiment: the challenge is not a publisher
signature or proof that the publisher reopened a file during the run.

## Run the example

From this revision, start the resource publisher:

```sh
go run ./cmd/metro-web-demo -addr 127.0.0.1:8788 -site-config ./examples/metro-web/site-007/site.json
```

In another terminal, run the separate checker:

```sh
go run ./cmd/metro-web-check -origin http://127.0.0.1:8788 -target spec
```

Run it twice to obtain two independently generated challenges. The checker
still validates the map, route, complete bytes, 64 KiB chunk digests, Packet,
Route, and Receipt fields. A successful result uses
`metro.web.independent-check.v0.2`, reports
`VERIFIED_BYTES_AND_CHALLENGE_BOUND_TRANSCRIPT`, and keeps
`run_freshness_verified: false` and `publisher_identity_verified: false`.
The challenge must be generated by the checker, not supplied by the publisher.

## Exchange and compatibility

After verifying the map and resource bytes, the checker draws 32 bytes from
the system cryptographic random source, encodes them as 64 lowercase
hexadecimal characters, and sends one request:

```json
{"target":"spec","client_challenge":"<64 lowercase hex characters>"}
```

The publisher echoes `client_challenge` at the top of the response and in
each event's `packet.action.inputs` and `result`. The existing Receipt input
and result hashes cover these fields. The checker compares every echo to its
own challenge and recomputes the hashes. A missing or different echo, or a
digest that no longer matches the changed fields, rejects the transcript.
The route-memory key does not include the challenge: remembered transition
IDs can be reused, but the demo makes new Packets, reads, and Receipts for
each run.

The request field is optional for older readers. A request containing only
`target` retains the Stage 007 response shape. An invalid, duplicate, null,
non-string, uppercase, or wrong-length challenge is rejected before a route
or resource read. The Stage 009 checker deliberately does not fall back to
an older publisher that lacks challenge support. The map remains
`metro.web.site.v0.1`; Metro Packet, Route, and Receipt formats stay at
`v0.1`.

## What the result means

The challenge rules out **byte-for-byte reuse of an old run response** for
this particular checker request. It does not rule out an active publisher
that receives the challenge and constructs a fresh, internally consistent
response from cached file bytes. Receipt hashes are unkeyed SHA-256 values;
they do not authenticate the publisher. A successful check does not prove
that the publisher actually reread its files, that the files contain true
information, or that a real-world publisher has a particular identity.

The demo does perform fresh pinned reads. The independent checker verifies
the bytes returned by its own requests and the consistency of the demo's
transcript, not the demo's internal execution. Authentication and
independently observable execution freshness need separate trust mechanisms.
The checker never uploads, writes, executes publisher content, or follows
publisher-provided URLs.

## Verification

```sh
go test -race -count=1 -timeout 120s ./cmd/metro-web-check ./cmd/metro-web-demo ./internal/metro
go vet ./cmd/metro-web-check ./cmd/metro-web-demo ./internal/metro
```

Tests cover different challenges on consecutive checks, rejection of old
or altered transcripts, strict request parsing, the legacy request shape,
and challenge binding on graph and remembered routes. A local test is still
not an independent outside-developer report.
